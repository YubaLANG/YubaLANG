# YubaLANG 1.3.0 release notes

YubaLANG 1.3.0 brings the language up to a stable 1.3 baseline with clearer
syntax, stronger runtime checks, and a more consistent set of language tools.
This release keeps the existing command-oriented style while adding expression
support, better diagnostics, and the formal semantics required for a more
predictable runtime.

## What is new in 1.3.0

### Expressions, assignment, and condition checks

The 1.3 language reference formalizes expression evaluation and assignment.
Programs can now use expressions in assignments, returns, output, comparisons,
and conditions instead of only using command-style arithmetic.

```hl
define var count: int = 2
define var total: int = 0
set total = (count + 3) * 4 - 2

if total >= 18
    text output "ready"
endif
```

The `set` command updates an existing variable without changing its declared
type. `if`, `elseif`, and `loop while` conditions must evaluate to a boolean.
Numeric and collection truthiness is no longer accepted implicitly.

Control-flow branches, loops, and exception-handling bodies now have lexical
scopes. Names declared in those blocks do not leak after the block ends, while
`set` updates the nearest existing binding. Function calls do not capture
variables from the caller's local scope. Nested functions capture defining
bindings by reference and can outlive their defining call.

### Stronger type and source diagnostics

YubaLANG 1.3 adds source-located diagnostic output for invalid conditions,
invalid assignments, unsupported syntax, and many static type mismatches.
`YubaLANG check <file.yl>` can now report syntax or type problems without
executing the program.

### Function and built-in improvements

The 1.3 baseline includes named arguments, defaults, and varargs in user
functions, as well as more consistent handling for typed results and collection
operations. Built-ins such as `format`, `map`, `filter`, `assert`, and
`compare` are covered by the interpreter and the test suite.

### Records, modules, and tooling

The runtime includes the documented record model, import semantics, protected
module namespaces, and a richer editor/LSP experience for completion,
references, quick fixes, and document diagnostics.
Module functions remain public by default; `func private define` can hide
module-level helpers from importers without preventing internal calls.

## Migration guidance from 1.2

The 1.3 release is intended to be compatible with existing command-oriented
code. The most important migration details are:

- Existing command forms remain supported.
- `set` is the new way to update an existing variable.
- Conditions must evaluate to `bool`; convert explicitly where needed.
- Variable names now follow Python-style Unicode identifier rules.
- String and collection values are validated more strictly at runtime.
- A `check` pass is available for opt-in static validation.

### Example migration

Before:

```hl
define var count: int = 2
arith add count 3
```

After:

```hl
define var count: int = 2
set count = count + 3
```

If older code used numeric or collection truthiness in a condition, convert it
explicitly before the condition check:

```hl
define var enabled: bool = false
if enabled
    text output "running"
endif
```

## Compatibility notes

- YubaLANG 1.3 continues to accept `1.2` project manifests.
- New projects created by 1.3 default to `yubalang: "1.3"`.
- Package-manager compatibility is intentionally kept separate from the core
  language/runtime release and is documented in the YubaPKG toolchain.

## Release scope

This 1.3.0 release is the language/runtime baseline for the 1.3 series. The
core language, interpreter, tests, documentation, and editor tooling are kept in
sync with the reference docs, while package-manager behavior remains a separate
concern to be finalized with the package toolchain.
